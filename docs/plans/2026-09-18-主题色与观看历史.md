## 先纠一个记忆偏差：那条"扣分"到底管什么

你说"扣分是为了解决各平台热度标准不同（抖音上亿播放 vs B站没有）"——这里其实是**两套机制**，
代码里各管一件事，后面要调参时别调错旋钮：

| 机制 | 位置 | 作用 |
|---|---|---|
| `platformRelativeEngagementScores`（互动分只在**平台内部**做相对排名） | `webui/src/lib/searchExperience.ts` | 解决你说的"抖音/B站量级不可比"——**这才是那个问题的解法** |
| `DIVERSITY_CONSECUTIVE_PENALTY` / `DIVERSITY_OVERREPRESENTATION_PENALTY` | 同上 | 纯粹让四个平台交替出现，跟热度无关 |

结论照你的意思：**两个都保持现状不动**。只提醒一句：以后若觉得"某平台明明内容多却被压得太靠后"，
要动的是 Diversity 那两个值，不是热度算法。

## 一、8 种主题色（加急）

### 现状（都已确认）

- 深浅由 `<html>` 上的 `.dark` class 控制，逻辑在 `webui/src/store/themeStore.ts`，
  持久化键 `mediacrawler_theme`（`light` / `dark` / `system`）。
- 品牌色现在是一组变量：`--brand` / `--brand-2` / `--brand-soft` / `--brand-ink`，
  外加 shadcn 那套 `--primary` / `--accent` / `--ring`——目前全是同一支蓝。
- **硬编码颜色存量**（这是换主题唯一会咬人的地方）：
  `index.css` 60 处、`Header.tsx` 11、`AccountsPage.tsx` 5、`LicenseDisclaimer.tsx` 4、
  `SearchPage.tsx` 1（字标渐变）、`types/search.ts` 4。
  其中 `types/search.ts` 那 4 个是**平台自身品牌色**（小红书红、抖音黑…），
  **不跟着主题变**，别顺手一起抽了。

### 做法

1. **抽一层 accent 变量**：把 brand 系列 + primary/accent/ring 收敛成"随 accent 覆盖的一组变量"，
   每种主题色 = 一小段 CSS（约 8–12 行），挂在 `html[data-accent="graphite"]` 这样的选择器上。
2. `themeStore` 加第二个持久化键（沿用既有前缀风格，例如 `mediacrawler_accent`），默认湛蓝，
   与现有 `light/dark` 并存 → **主题色只管色相，深浅仍是独立开关**（这点见下面的待确认）。
3. 把 `index.css` / `Header` / `AccountsPage` / `LicenseDisclaimer` 里约 20 处**品牌色**硬编码换成变量；
   中性灰与平台色不动。（正好清偿之前记下的"别手写颜色值"那笔债。）
4. 8 个色建议名单：湛蓝（现状）、**石墨黑（ChatGPT 那种黑白感）**、松绿、赭橙、玫瑰、紫、青、酒红。
   每色要给 light / dark 两套值，因为同一个色相在深浅底上的可读值不一样。

### 布局：你说的"放在自定义页面左边"，我需要确认一下

现状是「自定义」= 设置里的**外观与首页**那一屏：左边一个竖排入口栏
（搜索设置 / 账号与登录 / 外观与首页），右边是内容区，色卡现在在内容区顶部。

- **A：色卡留在右侧内容区顶部**，改成 8 个色块网格，下面才是深浅 + 首页模式。改动最小。
- **B：色卡移到左栏**竖排，右侧放实时预览。更像取色器，但要动侧栏结构。

我倾向 **A**：8 个色横着排才好挑，塞进窄左栏会挤成一列、也跟上面三个入口抢视觉重心。
你说一声是 A 还是 B。

### 待你拍板的两点

1. **主题色要不要连带改深浅？** 选"石墨黑"时，是"石墨 + 保持你现在的深浅"，还是"直接切到深色模式"？
   我建议**只管色相**，深浅继续由主题开关控制——不然 8 个色里有几个是暗色系，选完就黑屏会很突然。
2. **8 个色的具体名单**（上面那份只是建议，你说换就换）。

### 影响面

- 新增 i18n 键必须**中英双语同加**（`tests/test_webui_ui_contract.py` 会卡键集合一致）。
- `webui/tests` 里若有断言主题按钮数量 / `theme-card` 的，要同步。
- `docs/features/` 里没有独立的"外观"文档，这轮顺手在合适处记一笔（或新建）。
- **对比度只能人眼看**，本机没有 Playwright 浏览器，8 色 × 深浅的真机观感要你亲自扫一眼。

## 二、观看历史

需求：自动记录，用户点链接发生跳转就把这条内容记下来；入口放在「收藏」和「设置」之间。

### 一个必须提前说的设计决定：**不能复用收藏表**

`items` 表是收藏库（`api/services/library_store.py`，`UNIQUE(platform, content_id)`），
而**「全部」视图包含库里每一条内容**，哪怕它不属于任何收藏夹。
把浏览记录写进 `items` 等于"自动收藏"——历史会污染收藏。

所以：**在同一个 `library.db` 里新建 `views` 表**（复用 `SqliteStoreBase`，跟 `remote_favorites_store`
同套路），字段照 `items` 的内容列，去掉 `note` / `in_default` / `watch_later`，
加上 `first_viewed_at` / `last_viewed_at` / `view_count`。
（这条纠正了早前"复用同一张表加个 `viewed_at`"的粗略说法——那时没看「全部」的语义。）

### 触发与上限

- 触发点：`ResultCard` 的链接 `onClick` → `POST /api/history`。**失败静默**，绝不能因为记历史挡住跳转。
- 去重：同一条再看只更新 `last_viewed_at` 和 `view_count`，不重复插入。
- 上限：**滚动淘汰 1000 条**（收藏是 500 条上限；历史可以更宽松，但必须有上限，否则库会一直涨）。

### 页面与入口

- `ViewMode` 加 `'history'`；`App.tsx` 的 `routeFromHash()` 支持 `#/history`；
  `Header.tsx` 的 `navItems` 在「收藏」和「设置」之间插入「历史」。
- 新 `HistoryPage` **复用 `ResultTabs` 渲染卡片**（收藏页就是这么做的），
  按最近浏览倒序，支持按平台筛选、删单条、清空。

### 待你定的一点

**要不要一个"暂停记录"开关？** 历史是自动记的，加一个开关成本很低，
但能回应"它在偷偷记我看过什么"的顾虑（数据只在本机 `library.db`）。我倾向加，放历史页右上角。
你说不加的话就不做。

### 工作量拆两步（有依赖，建议串行）

1. **后端 + 存储**（可独立测）：`api/services/history_store.py` + schema + `api/routers/history.py`
   + `api/schemas/history.py`，配套 `tests/test_history_store.py`。
2. **前端**：记录 hook、`HistoryPage`、导航入口、i18n 双语。
