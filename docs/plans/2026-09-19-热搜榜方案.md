## 一、先把这件事想清楚：用户要的到底是什么

你最初的原话是「**热搜榜功能：看各平台对某热搜的不同反应**」。

这句话里藏着一个重要的取舍：**用户手机上本来就能看各平台自己的热搜**，我们搬一份榜单过去没有价值。
有价值的是后半句——**同一条热搜，四个平台分别是什么反应**。而这恰好就是四野已有的能力：
一个关键词，四个平台并行搜索，合并成一页。

所以这个功能的定位建议是：

> **热搜榜不是"榜单浏览器"，而是"搜索的入口"。**
> 榜单只需要提供**词**（+ 平台、热度、可选原链接），点一条 → 直接丢进现有的四平台聚合搜索。

这样定位和"搬榜单"相比：

| | 搬榜单（不推荐） | 热词 → 聚合搜索（推荐） |
|---|---|---|
| 需要的数据 | 词 + 内容 + 作者 + 指标 + 图 | 只要**词** |
| 需要新写的抓取 | 四个平台的榜单详情解析 | 一个"取热词"的轻量接口 |
| 渲染 | 新的卡片列表 | 点一下就走现有搜索链路 |
| 失败的影响 | 平台不可用就是空白 | 少一列词，其余照常 |

**结论：只取词，不取内容。** 内容交给已有的搜索去做。

## 二、代码现状（这些是查过的，不是猜的）

- **worker 已经支持多种任务模式**：`aggregate_search/models.py` 的 `WorkerRequest.mode`
  现在是 `Literal["search", "login", "favorites"]` —— 加一个 `"trending"` 是自然的扩展点，
  不用另起一套进程模型。
- **两个平台本来就"不依赖登录也能搜"**（worker 里写死的）：
  - 抖音：provider id 是 `public_search`，`allow_public_search=(core_platform == "dy")`；
  - B站：走 `light_api`，且**不要求有会话快照**（对比小红书要求 `session_snapshot` 才走 fast path）。
  → **这两个平台的热榜最可能也不需要登录态**，是首选试点。
- **小红书最贵**：请求要 `X-S` 签名，签名由 `media_platform/xhs/playwright_sign.py`
  用浏览器算出来；B站部分接口要 wbi 签名。所以小红书热榜大概率要登录 + 浏览器，成本最高。
- **结果缓存不能直接复用**：`api/services/result_cache.py` 的 key 带**账号代数**、TTL 夹紧在
  [60,120] 秒，语义是"搜索结果只短暂复用"。热榜应该有自己的缓存（见下）。
- **不能污染收藏库**：热榜是易失数据，只进内存缓存，不写 `library.db`。
- 前端现在的「推荐搜索」是 `webui/src/lib/searchPopover.ts` 里**写死的五个词**——
  这是最现成的替换点。

## 三、候选接口（**以实测为准**，先别信我列的路径）

### ✅ 抖音：已实测可用（2026-09-19）

| 项 | 结果 |
|---|---|
| 接口 | `https://www.iesdouyin.com/web/api/v2/hotsearch/billboard/word/` |
| 需要登录吗 | **不需要**（不带任何 cookie，实测 200） |
| 需要签名吗 | **不需要**（连 `a_bogus` 都不用带） |
| 需要浏览器吗 | **不需要**，纯 HTTP 即可 |
| 返回 | `word_list` 50 条，每条 `{word, hot_value, label}`；另有 `active_time`（榜单更新时间） |

顺带排除掉的：web 端的 `/aweme/v1/web/hot/search/list/`（带不带 `a_bogus` 都是 **200 + 空 body**），
说明那条路要 cookie/其它条件，不必走。

另外确认了一件事：`a_bogus` 是用 `execjs` 跑 `libs/douyin.js` **在进程内算出来的，不依赖浏览器**
（只有 `msToken` 取自 localStorage）—— 所以将来若有别的抖音接口要签名，也不一定要起浏览器。

**注意**：抖音榜**分钟级**在动（实测 `active_time` 与请求时间只差 2 分钟），
所以缓存别设太长，**建议 5 分钟**，并且允许用户手动刷新。

## 四、做法（分三步，每步可独立交付）

### 第 1 步：spike（半天，只验证不落地）

用 `tools/httpx_util.py` 同款方式（或现有 client 的 get/post）直接打候选接口，回答四个问题：

1. 不带任何 cookie 能不能返回？返回什么字段？
2. 需要签名的，现有签名能力（`playwright_sign` / wbi）能不能直接复用？
3. 频率限制有多严（连打 10 次会不会 412/461/471）？
4. 榜单多久更新一次（决定缓存 TTL）？

**产出只有一份记录**：每个平台「可用 / 不可用 / 需要什么」，写进本文档，再决定第 2 步做几个平台。
这一步不做完，后面所有估工都是猜的。

### 第 2 步：最小闭环（推荐先只做 1–2 个平台）

- 后端：新增 `GET /api/trending` → 返回 `{平台: [{词, 热度, 链接}]}`。
  - 优先在 **API 进程内**直接请求（公开接口不需要浏览器/worker）；需要签名的平台再走 worker 的 `trending` mode。
  - **独立缓存**：TTL 建议 10 分钟（榜变慢、请求要省），容量小、只存词；
    与 `result_cache` 分开，别把账号代数那套语义带进来。
  - **独立限流**：热榜请求**不进** `search_metrics.PlatformCooldowns`（那是搜索的冷却，
    别让看榜把搜索搞进冷却）；单个平台取不到就只缺那一列，其余照常返回。
  - 错误只给安全文案，不回显响应原文、不打 cookie（沿用 `aggregate_search/protocol.py` 的脱敏）。
- 前端：把首页搜索框浮层里**写死的推荐词换成真热词**（成本最低、立刻可见）；
  点一个词 → 走现有的"只填词、不自动搜索、保留当前平台勾选"行为。

### 第 3 步：再做大（按你反馈决定）

- 独立入口：导航加第 5 个「热搜」（现在是 首页 / 收藏 / 历史 / 设置）。
- 四个平台并列展示同一批热词 → 直接看出"谁在热、谁没反应"。
- 小红书要不要做（取决于 spike 出来的成本）。

## 五、必须提前说清的边界与风险

- **接口会变**：热榜是平台没承诺过的内部接口，随时可能失效。所以每个平台都要能单独降级，
  一个平台挂了不能让整页空白。
- **不带登录态**：公开接口不带 cookie，也就不碰账号验证、不占"账号/搜索互斥租约"。
- **不追求实时**：热榜本来几分钟才变一次，缓存 10 分钟完全够，也顺便规避频率风险。
- **不落库、不上传**：纯内存缓存，进程退出就没了。
- 合规：只取"词"这一层，不做内容抓取的额外放大；频率比现有搜索还要保守。

## 八、分平台还是聚合？（已定：数据层分平台）

**数据层必须分平台，聚合只能发生在展示层。** 理由是聚合不可逆：一旦丢掉平台归属，
就再也答不出"这个词是谁在热"，而这个功能的价值恰恰在"各平台的不同反应"。
从分平台数据算一个合并视图随时可以，反过来不行。

具体落地：

- `GET /api/trending` **按平台返回**（`{xhs: [...], douyin: [...], ...}`），前端想怎么摆都行。
- 第一个版本的浮层推荐词：**按平台分组**（每个平台出 top 3–5），而不是把 4×5 个词混成一锅。
  混在一起既看不出差异，也会把浮层撑得很长。
- 以后若做独立面板，可以再加一栏"**多平台共识词**"（几个平台同时在热的词）——
  那才是"聚合"真正有价值的地方（发现全网都在讨论的事），属于第二期。
- 还有个现实理由：各平台字段不一样（抖音是 `hot_value` 热度值，B站可能是播放量，
  知乎/小红书未知）。硬聚合成一张表要先做一层归一化，而这一层对"点词去搜"毫无帮助。

## 九、看完实测数据后，我对入口 A 的一个保留意见

实测回来的抖音榜单前几名是这样（13:43 的原始数据）：

```
中国女篮111:46大胜泰国        沙特首都利雅得遭空袭
以好房助安居                  来大理追一场会游动的洱海星河
起猛了创大要打百分了          这个中秋打卡安徽鳌鱼灯
```

也就是说：**热榜前几名大量是时政 / 新闻类词**。而入口 A 的位置是搜索框浮层里的
「推荐搜索」——那里的语义是"帮你想想搜什么"（现在是"剪辑入门""露营装备"这类兴趣词）。
把新闻塞进那里，语义是错位的：用户点进去会得到一堆新闻聚合，而不是四野擅长的
"看不同平台对同一件事的不同反应"。

所以我建议：

- **技术闭环照 A 做**（最省，能立刻看到真词），但**正式形态建议加一个首页「热搜」面板（入口 B）**，
  语义正好是"看各平台在热什么"；
- 或者 **A 收窄**：浮层里只放榜单里偏内容/生活向的词——但"哪条是新闻"没有可靠的自动判据，
  我不建议自己造一个分类规则（做不准，还会引入维护成本）。
- 折中方案：**A 保留现有兴趣向推荐词不变，新增 B 面板承载真热词**。
  这样既不破坏搜索框的语义，也让热榜有正确的位置。

这条是我在拿到真实数据之后才发现的，跟你选 A 时的判断依据不同（当时我说 A"最省"，
但没看到榜单内容）。要不要按这个调整，你定。
