# 决策：单平台重搜（⟳）——替换当前批次里的该平台，不开新批次

- 日期：2026-09-19
- 状态：已实施（本文件记录了三版取舍，最终版本见"决定"）

## 背景

用户的实际场景：这一轮只搜了抖音 / B站 / 知乎，看过结果之后**只想补看小红书**
（或把某个平台重搜一遍），不想让其它平台重搜、不想结果被清掉重来，
**更不想多出一批**——因为多出一批就等于"这一页只能看那一个平台"，
还得靠"换一批"来回切才能对比，那就白做了。

## 走错的两版（都实现在前、被用户当场否掉）

1. **接到既有的「单平台重试」链路上** → 它其实是"在会话里继续抓这个平台的下一批"，
   后端有"换批不能新增平台"的守卫，界面直接弹错。
2. **改成"并进会话 + append 合并"** → 虽然能补进结果，但走的是续跑提交，
   后端**新增了一批**，界面出现"第 1 批 / 第 2 批"，用户看到的还是单平台那一批。
   而且 append 的语义（保留旧内容）也不是用户要的——用户说的是"**替换**掉这一批的结果"。

## 三个动作的语义（最终定稿）

| 动作 | 做什么 | 会不会多出一批 |
|---|---|---|
| 换一批 | 每个平台往后翻页，**不重合**的新内容 | **会**（第 2 批、第 3 批往后叠加） |
| 刷新结果 | 整组**重搜一遍**，允许重合，替换当前视图 | 不会 |
| **单平台重搜（⟳ / 重试）** | **只重搜这一个平台**，替换它在当前批次里的内容 | **不会** |

## 决定

`POST /api/search/jobs` 新增 `replace_platforms: bool`：

- 带 `continue_from` + `replace_platforms` → **单平台重搜**：
  - 重置该平台在会话里的分页进度（从第 1 页重搜）、账号代数更新为当前值
    —— 顺带解掉两个死结：①上一轮它一条没搜到却被判定"取尽"时点不动；
    ②用户刚补登账号再来重搜时被"账号状态已变化"挡住；
  - 提交时**原地替换**该平台结果（`Exploration.replace_platform_results`），
    `round` 不变、不新增批次；
  - 响应带上会话里其它平台的状态（`response_statuses`），平台状态条与各平台条数不会只剩一个。
- 不带 `replace_platforms` 的 `continue_from` → **换批**，保持原样：
  平台必须在会话里（否则仍然拒绝），往后叠加新批次。
- 前端 ⟳ 与平台卡片上的「重试」统一走 `handleFetchPlatform`（同一个函数），
  走 `retry_*` 事件：**不写历史、不改搜索范围勾选**，合并用 `mergeSinglePlatformRetry`
  （替换该平台在该批次里的内容）。

## 后果

- 上一版的 `mergeSinglePlatformAppend` 与 reducer 的 `retryingMode` 字段已删除（没用了，
  留着是债）。
- 「重试」按钮不再受"这个平台还有没有更多"限制：它现在是重搜，不是续抓。
- 单平台重搜会**丢掉该平台在本会话里已累计的内容**（被新结果替换）——这是用户明确要的
  "替换"，代价是如果新结果比旧的少，看起来会变少。
- 单平台重搜之后，「换一批」仍然可用（会话没有被打断）。
- 边界：会话过期（后端换了活动任务）时单独重搜会返回"上一轮已失效，请从当前搜索继续或重新搜索"。

## 又踩的一坑（同日，v3 之后的 hotfix）：重搜响应必须是**整轮全量视图**

v3 刚上线就被用户抓到：重搜小红书后，其它平台的 40 条从页面上消失了
（状态条还显示"B站 20 条"，点进去却是空的）。

根因是 `replace_platform_results` 把 `_final_results` 设成了**只有被重搜平台**的新结果，
而「换一批」的 `commit()` 给的是**全部平台累计结果的交错视图**。前端有两条路都会
拿这份响应覆盖展示：单平台合并（自洽）和**终态提交后的补全（hydration）迟到轮询**
（同 job_id 整体替换 `jobResponse`）——后者把刚合并好的结果整批盖掉。
状态条没事是因为 `response_statuses()` 带上了全部平台状态，才出现"显示 20 条、
点进去没有内容"的割裂。

修法（两道）：

1. 后端：`replace_platform_results` 与 `commit()` 同构 —— `_final_results` 与
   `batches[-1]["results"]` 都用 `self.results`（全部平台）交错出的完整视图。
   **凡是会话提交，响应永远是整轮视图**，这条不变式写在这里。
2. 前端：终态提交后同一 job 的补全轮询加护栏 —— 同一个 job 的响应结果**不应变少**，
   变少就保住当前结果列表（只更新补全状态/摘要）。

## 再踩一坑（同日第三修）：重搜合并的快照必须带回 `exploration`

用户连续重搜多个平台时再次出现"新平台出来了、之前的平台没了"。根因不在合并算法，
而在**重搜合并构造的快照丢掉了 `exploration` 字段**：

- 下一次重搜靠 `current.exploration` 判断能否续会话（带 `continue_from`）；
- 字段一丢 → 第二次重搜变成**独立单平台搜索** → 后端起全新会话并整体替换 `_active_job`；
- 从此每次重搜的"整轮视图"只剩那个新会话里的平台，其它平台清不回来 ——
  连锁反应，直到整组重搜。

修法：重试合并的快照带上 `exploration`（取本次响应的，兜底用上一份快照的），
顺带透传 `hydration_status` / `total_ms`。**凡是从旧快照派生新快照，会话身份字段
必须显式继承**，这条和"响应是整轮视图"配对成立。

另有一个连带小修：replace 任务的详情补全此前必然 `KeyError`
（补全范围用了全量视图，但 `platforms_state` 只有本任务平台）——
补全范围改为"本任务跑过的平台"。
