# 决策：账号页主结论「可用 / 不可用」与三处盲区处理

- 日期：2026-09-18
- 状态：已实施

## 背景

账号页被用户反馈"信息一锅粥"：一次成功搜索要过 7 道关卡（本机浏览器可用 → 本机有登录态 → 真实验证过 → 搜索时仍有效 → 没占着 profile → 没在冷却 → 搜索路径走得通），但卡片把这些都平铺在同一张卡上，且有三处盲区（浏览器不可用、平台冷却中、抖音公开搜索规则）一声不吭。本次只改账号页的"呈现"，方向是：卡片主结论一句话——「可用 / 不可用」（不可用给最短原因），所有具体原因、过程、诊断折叠进「详情」，每张卡变成"动作卡片"（现在该点哪个按钮，或为什么现在不能搜）。

## 选项

- 主结论与详情的判定数据来源：前端能否拿到？`/api/health` 能拿浏览器可用性；平台冷却 `cooldown_until` 只在搜索 job 响应里，账号页拿不到；抖音允许公开搜索是静态产品规则（worker 对 dy 开 `allow_public_search`）。
- 拿不到冷却数据时：要么后端补字段（大改，违背"不要为补一个字段大改后端"），要么本轮不做并在文档/决策里写清。

## 决定

- 主结论与动作提示做成纯函数 `accountSearchVerdict` / `accountActionHint`（`webui/src/lib/accounts.ts`），账号页只渲染三态徽章 + 一行主结论 + 一行动作提示，其余全部收进「详情」。
- 关卡 0（浏览器可用性）：通过给 `useAccounts` 增加 `browserAvailable` 字段（来自 `/api/health`）补上，账号页顶部加红色提示，每张卡主结论也体现。
- 抖音公开搜索：作为静态规则，在抖音卡主结论标「可用 · 抖音允许公开搜索」，详情补充"未登录也可能出结果"。
- 关卡 5（平台冷却）：账号页不展示（数据不在账号接口里），不在前端编造；冷却状态仍由搜索结果页体现。需要时在后端 `GET /api/search/accounts` 增加冷却字段后再补。
- 不引入新的 i18n 键（沿用现有硬编码中文），不改 `search/*`、`help/*`、引导与 `App.tsx`；新增样式只用现有 token（`text-ok`/`text-danger`/`text-warn` 等），不手写颜色值。

## 后果

- 账号页更简洁：主结论一眼可见，普通用户不再被"非实时检测"标题劝退（已改为「排查诊断」并保留小字说明）。
- 仍有一个真实盲区（平台冷却）本轮未在账号页体现，需在报告与本文档显式说明，避免误以为"全补上了"。
- 新增 `useAccounts` 的 `browserAvailable` 字段为可空（null = 尚未确定），不影响既有 `apiRunning` 语义与其他消费者。
- 受 `tests/test_webui_ui_contract.py` 的"状态文案单一来源"约束，账号页仍在「详情」复用 `accountCardStatusLabel`，未另起第二套状态映射。
