# 决策：抖音收藏改为页面内读取

- 日期：2026-10-27
- 状态：已实现；真实账号实测 64 条四页完整读取，日常 EXE 未重建
- 相关：`docs/features/remote-favorites-sync.md`、`docs/decisions/2026-10-10-阅读复用官方页面响应.md`

## 背景

抖音收藏同步在 `0a9c951` 之后一直不可用。2026-10-27 的只读探测把它定位到一个比"签名算法不对"更具体的原因：

- 同一会话里，后端签名的 `GET /aweme/v1/web/user/profile/self/` 返回 200 并给出本人 `sec_uid`；
- 后端签名的 `POST /aweme/v1/web/aweme/listcollection/` 返回 **HTTP 403**，正文不是 JSON，而是 `Blocked by ArgusSecurityPlugin Uifid Not Found`；
- 官方收藏页自己发出的同一请求是 200。

也就是说，收藏列表由页面上下文里的 Argus 安全插件按 `uifid` 校验，后端自拼的 `a_bogus` 与页面实际发出的请求不等价。补 `UIFID` 请求头只会把错误换成 `Signature Not Found`，`x-secsdk-csrf-token: DOWNGRADE` 也不够 —— 缺的是页面那套完整签名，不是某一个头。另一个容易误判的点：从**首页**发出的页面内 `fetch` 同样 403，必须是已经导航到 `/user/self?showTab=collection` 的页面。

## 选项

- 继续修补后端签名（补 `uifid`、对齐 `fp` / `verifyFp` / `x-secsdk-web-signature`）：逆向成本高，且平台一改就再次失效；本轮已证明单补请求头只会换一个 403 文案。
- 复用官方页面在正常浏览时自己发出的收藏响应：需要用户手动翻完整个收藏列表，做不到完整归档。
- 在已登录的官方收藏页内部 `fetch` 同一端点，只保留适配器需要的公开字段。

## 决定

采用第三项。请求、Cookie、签名都由用户自己的已登录页面发出，`media_platform/douyin/collection.py` 负责导航到收藏页与预热重试，`libs/douyin_collection.js` 负责读取并把每行投影成有界字段（公开 CDN 地址、公开计数、发布时间、时长）。与[阅读复用官方页面响应](2026-10-10-阅读复用官方页面响应.md)同一思路：不另造通道，也不主动重发后端签名请求。

账号身份仍然走平台自己的 `profile/self` 接口（该接口后端可直连），因此"收藏能读"与"能确认是谁"是两条独立证据：只有 `profile/self` 明确无本人对象才判定登录失效；收藏页没就绪、结构异常一律按可重试失败处理，绝不改写账号状态。

## 后果

- 收藏同步需要打开一个抖音浏览器页面并导航到收藏页，比纯 HTTP 路径慢；预热窗口（实测约 1.6 秒内仍 403）由重试覆盖，耗尽后提示"稍后重试"。
- 增量停点保持关闭：分页顺序只在一次真实账号上验证过，多读的代价只是时间；普通同步本来就不删旧内容。
- 列表没有 `collect_time`，归档只有发布时间，不伪造收藏时间。
- 官方页面结构与安全插件仍会变化；页面改版可能让读取再次失效，届时应先看 `Blocked by ArgusSecurityPlugin ...` 的具体文案，再决定是补上下文还是换路径。
- 本轮没有重建日常 EXE，也没有跑界面验收；源码路径与真实账号读取已验收。
