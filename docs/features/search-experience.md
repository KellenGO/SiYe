# 搜索体验（列表与封面网格 / 排序 / 去重 / 渐进展示）

## 一句话

一次搜索会把四个平台的结果合并成**一页**：先流式展示已经回来的平台，边搜边显示进度；
再按用户选的排序方式重排、跨平台去重、按平台分组，并把活动指标（点赞/播放等）补全后更新卡片。

## 代码入口

平台客户端共用 `base/search_context.py` 的请求上下文与重试边界；`aggregate_search/pagination.py` 保留兼容导出。抖音响应分类在 `media_platform/douyin/response.py`，分页无需加载 crawler。

常驻 worker 的启动、复用、请求上限及空闲回收在 `api/services/search_worker_supervisor.py` 的 `PlatformWorkerSupervisor`；搜索任务管理器保留兼容导出并负责业务状态。

## 关键决定

- 可信且身份匹配的小红书、抖音、B站普通视频及知乎回答／文章支持[站内阅读与播放](content-reading.md)：列表标题与封面打开阅读详情，网格沿用详情入口；仍提供原平台链接。内容按需读取，不在搜索期间批量预抓。知乎搜索响应本来就有的正文经私有事件在本次后端运行保留，正文及页面状态不进入公开搜索响应或分页快照，不新增平台请求。可展示正文取得或纯视频开始播放后才记录观看，失败不将摘要冒充全文。
- 知乎回答在搜索综合页及知乎页按问题编号合成问题卡片，与跨平台内容版本合并分开处理，原始回答身份和搜索分页保持不变。卡片显示问题标题、注明作者的回答摘要和当前搜索已获取回答数；筛选作用于具体回答，展示位置沿用命中结果的既有排序。打开详情后补充的回答只在问题阅读列表中展示，不改变原搜索结果数量或顺序。
- 问题卡片的收藏／稍后再看／空间入口先进入回答选择，批量工具按回答勾选、不默认全选问题下的回答；导出仍展开为回答来源。已保存内容及历史维持原有回答条目，不迁移成问题条目。口径不明的回答浏览量不再参与新结果指标补全或展示；问题浏览和总回答数缺失时不补造。

- 搜索页可开启当前[研究空间](spaces.md)，在列表、网格和详情一键加入资料；加入不影响收藏或稍后再看。搜索旁可展开该空间的富文本总笔记，查看详情时继续在旁边编辑。空间名不绑定搜索词，切换空间不重置当前搜索结果。

- **优先减少重复工作来提速**：小红书、B站、知乎的浏览器路径成功返回内容后，会话只留在当前常驻 worker 内存，后续关键词优先复用。调用方会话变化时丢弃旧副本；快速请求异常时清除副本并遵守原有回退规则，风控和已经输出部分结果仍不整轮重跑。账号操作会停止对应 worker，进程回收也会清除副本；不持久化新凭据文件、不常驻浏览器。取舍见 `docs/decisions/2026-09-30-搜索减少重复启动与等待.md`。
- **翻页仍保留原有最小间隔**：从上次请求结束计时，浏览器回退准备和结果处理已经花掉的时间计入间隔，避免准备完再完整等待一次。请求次数上限、风控冷却不变。
- **抖音按剩余目标请求，每页最多 20 条**：默认搜索 20 条时尝试一页拿齐；平台少返回、混入非内容项或去重后不足时继续分页，不把请求数量当作实际数量。平台是否采纳此数量需真实账号观察。
- **换批和单平台重搜可直接消费已取回的页尾**：同一账号代数下，剩余内容足够或已到末页时在后端本地去重回放，不启动 worker；不够时继续原有取页路径。不会重复上批内容，也不会用旧账号余量。
- B站聚合搜索在同一个 API client 中短暂复用已取得的 HTTP 签名参数（最长 60 秒），避免每页重复查询；其他操作保留原有行为。
- **首条体验以实际卡片可见为准**：前端先立即查询，之后在同一查询接口等待变化；后端收到一条结果就唤醒等待者，不等某个平台凑满、其他平台结束或详情补全。无变化时请求有界等待，避免高频空查；完成后停止。旧后端仍兼容 250 毫秒搜索轮询 / 800 毫秒详情补全轮询。这只改变本机通信，不增加平台请求。
- **单平台重搜也渐进展示**：首条新内容到来后只替换目标平台，其他平台保留；尚无新内容时保留旧结果。后续失败也保留已显示的新内容，无新内容的失败才保留旧内容。正式提交和探索分页仍等任务完成，旧任务迟到响应不覆盖新任务。
- **新关键词回到全部结果并清除结果内筛选**，避免先回来的平台被上次标签或旧筛选遮住。同一关键词的刷新、换批、单平台重搜保留当前标签和筛选，排序及列表／网格偏好不变。

- **双视图共用视觉语言**：列表保持详细阅读、网格保持封面浏览。两者沿用同一字体与颜色，封面圆角一致；列表以正文摘要区的常见高度为基准，确定封面高度，统一按 16:9 裁剪铺满，可用空间不足时等比缩小；网格统一为 16:9 并裁剪铺满；列表以紧凑缩略图复用缺图占位、知乎主题卡与小红书地址回退。类型与可靠视频时长放封面，列表多项指标放正文，网格只显示主要指标；两者统一 k / M / B 与近似值 ≈，悬停和无障碍名称提供完整数值及播放／阅读含义。平台品牌圆点与名称一致，聚合内容均标明平台版本数，不累加各来源数据。
- 列表的平台身份独立显示，摘要、作者和时间仍可阅读，长内容可行内展开；操作在右侧竖排，按钮与图标放大便于辨认和点击；窄屏封面放在正文上方，按钮仍留在右侧。两种视图的操作尺寸、焦点及批量选中轮廓一致，收藏与稍后再看仍独立。切回列表恢复已展开条目，新任务或页面范围变化时清理展开状态；切换不主动滚动或搬移焦点，页面变短时允许浏览器自然限制滚动位置。

- 视频有可靠时长时，在封面右下角显示分秒或时分秒；接入 B 站、抖音、小红书视频及知乎独立视频在已有响应中提供的时长，不为此追加请求。小红书已识别为视频的内容可读取视频流中以毫秒计的时长；缺失时不显示、不推算，也不回填旧收藏。图文配乐和回答、文章内嵌视频的时长不作为整条内容时长。时长随历史、收藏和备份快照保留，旧数据兼容。
- 小红书搜索响应可能完全不带视频时长，发布时间角标不能当播放时长。已有简介补全取得详情时，也提取缺失的可靠视频时长并同步平台结果与分组来源；详情没有简介但有时长也会刷新。保持原有补全候选、最多前 12 条及超时限制，不为缺时长新增请求；未被选中、详情失败或详情无时长的内容仍不显示时长。
- 封面底部不铺整条黑色渐变，封面类型、指标与时长字号加大，仅用文字阴影辅助阅读；时长独立靠右下角，左侧类型与指标可在窄封面中换行，不把时长挤到下一排。

- 详情抽屉中收藏成功后也自动弹出居中归属卡片；关闭卡片返回收藏按钮，抽屉保持打开。取消收藏、收藏失败与稍后再看不触发此弹窗。

- 封面底部使用带阴影的白色类型和指标，不铺整条黑色渐变。网格封面左下角、内容类型标签右侧，以列表同款图标加紧凑数字（k / M / B，如 15.4k、1.2M）展示一个已有主要指标，近似值用 ≈ 标识，悬停和无障碍名称保留完整含义：优先播放／阅读，其次点赞及其他已有互动数据，保留近似值标记；缺失不补零，真实零正常显示。聚合卡不叠加各来源数值，完整数据仍在详情查看。

- 两种视图中收藏成功后直接弹出居中的收藏夹归属卡片，可勾选归属并完成、按 Esc 或点击外部关闭。关闭不会撤销收藏；卡片下不插入收藏时间、备注或编辑入口，网格布局保持不变。收藏时间、归属与备注统一在详情内查看和编辑，列表不再显示重复的编辑横条。

- 内容视图开关使用简短的「列表 / 网格」。网格卡片的平台名称配主题色圆点，桌面上与原文及适用操作排在同一行；手机窄屏将操作统一排在平台下方。封面和标题继续打开详情，触屏保留较大的点击区域。

- **搜索结果支持列表 / 封面网格切换**：默认沿用网格，列表保留标题外链和行内展开；两种视图都可通过内容信息入口查看完整详情。网格点击封面或标题打开完整详情，展示已有简介、作者、时间及指标；未收藏也可查看。聚合卡标明平台版本数量，详情逐来源展示，支持分别打开原文、收藏和稍后再看。卡片操作始终可见，筛选高亮、排序、批量导出、平台页签及流式补全继续生效；详情读取更新后的结果，不以旧收藏快照覆盖当前搜索数据。无图、图片失败、无标题均有占位，缺失指标不补零。热搜只展示关键词，不采用内容网格。

- **平台顺序只有一个来源**（`webui/src/lib/platformMeta.ts` 的 `PLATFORM_SLUGS`，顺序即 UI 顺序
  `小红书 → 抖音 → B站 → 知乎`）。历史上这个数组在 8 个文件里各写了一遍，
  加一个平台要改 8 处 —— 2026-09-14 收敛成一份。
- **每平台数量上限 40、默认 20**，写在 `platformLimits.ts`，只存 localStorage
  （key `aggregate_search_platform_limits_v1`），坏值逐字段回退，不阻止搜索。
- **搜索结果缓存 TTL 默认 90 秒**，可用 `MC_RESULTS_CACHE_TTL_SECONDS` 覆盖并夹紧到 `[60,120]`，
  设为 0 关闭；容量 200 条 LRU。缓存 key 里带**账号代数**，所以账号同步/失效后旧结果自动作废。
- **平台限流后进冷却**：基准 60 秒，重复触发翻倍，封顶 300 秒（`PlatformCooldowns`）；
  只影响该平台，其他平台照常搜。
- **跨平台去重的阈值是刻意保守的**：标题最短 6 字（完全相同才放宽到 4 字）、
  模糊相似度阈值 0.9、摘要最短 20 字，另外会剥掉"（附完整文档）"这类标题后缀。
  宁可漏合并也不误合并 —— 合并错了用户看不出原因。
- **排序只作用于已返回的结果**，不会为了排序去额外请求平台。
- 搜索历史只留最近 10 条（`MAX_HISTORY_ITEMS`），存 localStorage。
- **某个平台这次没搜到就自动取消它的勾选**：搜索终态里出现 `failed` / `login_required` /
  `timed_out` / `rate_limited` 的平台会从当前勾选里移除，并写进持久化偏好（下次进来不再白搜一遍），
  同时弹一次**页面上方居中、品牌蓝、几秒后自动消失**的提示，说明原因与"已自动取消 xxx 的勾选"。
  **每轮搜索只弹一次**：去重记录在模块级集合里，切到别的页面再切回来（组件重新挂载、任务恢复）
  不会重复弹。结果区不再挂常驻黄卡——失败状态留给 `PlatformStatus` 的状态块，
  需要登录时弹窗给「去登录」出口。取舍见 `docs/decisions/2026-09-18-搜索失败提示与自动取消勾选.md`。
- **三个"重新拿结果"的动作，语义严格分开**（这三个很容易被做混，写代码前先看清楚）：

  | 动作 | 入口 | 做什么 | 会不会多出一批 |
  |---|---|---|---|
  | **换一批** | 结果区右上角 | 每个平台往后翻页，**不重合**的新内容 | **会**（第 2 批、第 3 批往后叠加） |
  | **刷新结果** | 「更多」菜单里 | 整组**重搜一遍**，允许与当前重合，替换当前视图 | 不会 |
  | **单平台重搜** | 搜索范围每颗胶囊右边的 ⟳，以及平台卡片上的「重试」 | **只重搜这一个平台**，替换它在当前批次里的内容；其它平台一条都不动 | **不会** |

- **单平台重搜（⟳）的实现**：`SearchBar` 的 `onPlatformFetch` →
  `useSearchExperience` 的 `handleFetchPlatform` → `POST /api/search/jobs`
  带上 `continue_from`（本轮 job）+ **`replace_platforms: true`**，只带这一个平台。
  后端按该平台在会话里的状态分三种走法（**重搜 = 单平台版的"换一批"**）：

  | 情形 | 行为 |
  |---|---|
  | 没搜过 / 一条都没有 | 从头搜（第 1 页）—— 补一个平台、或上轮空结果的平台 |
  | 有内容且还有下一页 | **接着该平台分页继续**，带已见 id 去重 → **与上一轮不重复的新内容** |
  | 有内容但已取尽 | 明确报"该平台已经取完，重搜没有新内容"，不静默返回重复内容 |

  - 完成后**原地替换**该平台的结果，`round` 不变、不新增批次；
  - **响应是整轮全量视图**（`self.results` 全部平台交错，与 `commit()` 同构）——
    绝不能只装被重搜平台，否则前端的快照/补全轮询会把其它平台的结果整批覆盖掉
    （踩过：状态条显示 20 条、点进去没有内容）；
  - 响应带上会话里其它平台的状态，平台状态条与各平台条数不会只剩一个。

  前端用 `mergeSinglePlatformRetry` 合并（整体替换该平台在该批次里的内容）。
  合并后的快照**必须带回 `exploration`** —— 丢了它，下一次重搜就不再续会话，
  后端起独立会话后其它平台的结果清不回来（踩过，见
  `docs/decisions/2026-09-19-单独获取某个平台.md`）。
  **平台是否勾选都不影响**：取消勾选某平台后想补看它的结果，直接点 ⟳ 即可，不用整组重搜；
  也**不会自动把它勾回来**、**不写搜索历史**。只有本轮已有搜索时才出现（需要一个关键词）。
  失败时提示只说"「小红书」这次没有取到内容"，不会谎称"已自动取消勾选"。
- **换批仍然不允许新增平台**（`换批不能新增平台，请重新搜索`）：那是"往后叠加一批"的语义，
  平台集合必须已经在会话里。"补一个没搜过的平台"走上面的 `replace_platforms`。
- **返回「首页」保留搜索状态**：首页的大搜索框只在还没有本轮结果时出现；
  搜过之后切到收藏 / 设置再点「首页」，回到的是切走前的结果页，不重置成初始首页。
- **首页 / 结果页可以往返**：结果页搜索框上方有独立的「← 返回首页」文字按钮，搜索框保持完整宽度。
  点了只切视图 —— **不清结果、不清任务、不动勾选**；
  带着结果回到首页时，搜索框下方会出现「查看上次搜索（N 条）」回到结果页
  （`.home-back-row`，与上面的搜索范围留出间距）。
  导航项「首页」恢复切走前的首页或结果视图，并保留输入、筛选、排序与滚动位置；重复点击不会重置。主动切回大搜索框使用「返回首页」，详情见[返回首页](back-to-home.md)。
  视图只在内存，不做持久化。入口：`SearchPage` 的 `view` 状态 / `goHome` / `showLastResults`，
  文案 `search.backToHome` / `search.viewLastSearch`。
  **首页不显示每颗平台胶囊的 ⟳**：那排平台在首页只用于勾选搜索范围，
  单独重搜只在结果页出现（`onPlatformFetch={!isHome && displayJobResponse ? … }`）。
- 桌面结果页把当前任务关键词、结果数和批次操作放在一处，下面依次是平台状态、筛选和内容。列表用紧凑的横向封面与操作区，网格给每列留出阅读标题的宽度。
- **"没搜到东西"算搜索失败**：`FAILED_PLATFORM_STATUSES` 含 `empty` —— 0 条的平台
  与失败平台同等对待（弹**页面上方居中**的提示卡片、自动取消勾选并写进偏好，每轮只弹一次）。
  提示里的原因**优先用平台自带的安全原因**（`info.error_summary`，例如抖音的"疑似平台风控"），
  没有时才回落到通用文案（`search.reasonEmpty` 等）。平台状态条也会显示同一条原因。
- **全局只有一个 sonner `<Toaster>`**：sonner 的每个 Toaster 实例都会渲染所有位置的分节，
  挂两个会把每条 toast 画两遍。需要顶部居中的提示在 toast 上显式传 `position: "top-center"`。
- 平台勾选：**按钮是勾选框，不是"能不能用"的状态灯**。偏好只有一条规则 ——
  **它就是用户最后一次勾的样子，含"一个都不勾"**（2026-09-23 收敛，见
  `docs/decisions/2026-09-23-平台偏好空数组语义.md`）：
  - 首次进入、存储里没有这个键 → 空集，四个平台都不预选，由用户亲手勾。
  - 此后每次勾/取消都立即落盘，刷新与页面往返都按上一次的勾选恢复。
  - **取消到零也照样落地**：零勾选是合法状态（首次进入就是零），点搜索时由 `SearchBar`
    提示"先勾选至少一个平台"，不禁用按钮。旧规则"至少保留一个平台"会让存储与界面分叉 ——
    用户把平台全取消、刷新后又被系统勾回来（用户没做过的动作）。
  - 平台搜索失败时页面会**自动取消这些平台的勾选**并写进偏好，所以零勾选也可能是这个原因造成的。
  - 只有**非数组 / 全部是非平台值**这类损坏值才回退全选，避免把用户卡住；"用户没勾"和"存储坏了"是两回事。
- 点击搜索框下拉层里的历史记录或首页「最近搜索」时，只把关键词填入搜索框并聚焦；不会自动发起搜索，也不会用历史平台覆盖当前勾选。历史平台只以「上次」标签提供上下文，实际搜索范围始终由用户当前勾选决定。下拉层只列最近搜索，不再提供固定的「推荐搜索」词（2026-10-21 移除：写死的兴趣词与实际搜索需求无关，且与首页热搜面板重复）。

- 视图偏好按搜索、历史、本地收藏、跨平台汇总、平台收藏夹内容五类页面分别保存在本机，互不联动；未保存或存储不可用时默认网格。切换只改变呈现，不重置搜索任务、关键词筛选、排序、平台、批量选择或已显示条数。旧文件夹导航偏好不用于内容视图。

- **平台失败只显示错误码，不摊开原因**（2026-11-05，用户明确要求）：界面与顶部提示
  只给「平台名 · 失败 · S0x」，具体触发条件与排查方法在 `webui/src/lib/failureCodes.ts`
  里按码索引 —— 那份表主要是给开发看的。后端 `error_summary` 是各平台随手写的一句话，
  长度与信息量都不一致、还会随版本漂移，直接摊给用户既不好看也不好比。
  **编码规则 `S` + 两位数字，只增不改、旧码不复用。**
- **排序切换是滑动分段控件**（2026-11-05）：与「列表 / 网格」同一套语言 —— 一个滑块
  在三个选项间平移，而不是原生下拉。滑块用 `transform` 过渡，不触发重排；
  `prefers-reduced-motion` 下关闭过渡。三个选项各带一句悬停说明（用户不必记算法，
  想了解时能一眼看到）。

## 已知坑 / 边界

- **取消的终态必须两端一致**（2026-10-21）：搜索已经完成、只剩详情补全时点取消，以前只停掉补全任务就 `return True`，不置 `_cancelled`、不 `finalize()` —— 接口回「已取消」，`GET /jobs/{id}` 却是 `completed`，刷新后又变回完成。现在这条分支走与普通取消相同的收尾：先 `_is_hydrating` 判断是否还有活，再停补全、按需置平台状态、`finalize()`，已搜到的结果保留。
- **结果反序列化失败要留痕**：worker 与后端字段漂移时 `UnifiedSearchResult(**rd)` 会整条失败。以前 `except Exception: pass` 静默丢弃，表现为「平台成功但条数偏少」，排查时被误判成风控。现在至少打一条 `dropped malformed <platform> result` 的 warning（只记平台、job id 和异常类型，不记内容）。
- 首次启动、worker 回收后仍有启动成本；平台网络、风控和实际返回的有效条数决定最终耗时。离线回归可验证少开浏览器、少发请求和不重复等待，不能据此承诺所有关键词固定几秒完成。B站即使复用了成功会话，平台仍可能要求浏览器路径。
- 平台列表通常按整页响应，第一条可用仍需等该次接口返回；即时展示不能消除这段网络耗时。平台状态卡里的「首条」计时截至后端收到内容，不等于点击到浏览器绘制的总时间。`search_first_result_smoke.py` 单独检查后端可用到卡片显示，并在剩余结果被阻塞时断言首条已经可见。
- **结果序号（`.result-number`）搜索页与收藏页共用同一套**：品牌色数字 + 上方 14×2px 短横线
  （`::before`），窄屏统一 `display: none`。样式写在 `.result-number` 本身，
  收藏页不再单独覆盖 —— 两边只差在收藏页多一条组间距和底色。（2026-09-21）
- 搜索框聚焦时用边框和浅色轮廓提示。圆角由外层 `.search-box` 提供，输入框本身保持矩形，避免裁切左端的光标。
  input 自己带 `border-radius: 9999px`（高 44px → 半径 22px）时，光标停在文本最左边
  （x=0，正在圆角收缩区）上下两端会被裁掉，看起来是"上下窄、中间正常"的一段弧线。
  改回矩形（`rounded-none`）即恢复正常，input 是透明的，外观没有区别。
  验证方法：聚焦输入框后截图，`caret="initial"`（Playwright 默认会把插入符隐藏掉）。
- **知乎搜索会混入非内容对象**：`search_v3` 的 `data[].object` 除回答／文章／视频外，还可能返回问题、用户等卡片。适配器只接受 `answer`／`article`／`zvideo`；独立问题对象没有可阅读或可收藏的正文，不进入搜索结果，前端问题分组也会跳过旧快照里的这类对象。否则空间操作在渲染时校验失败会导致白屏（2026-10-18 已修）。
- 搜索纯逻辑已按职责拆分；统一入口继续保留内部评分函数等既有导出，供现有调用方和回归测试使用。不能仅凭生产代码引用数量删除这些入口。
- i18n 覆盖情况（2026-09-15 更新）：`search.*` 命名空间的键**已在搜索页、搜索框、搜索浮层接线**
  （`webui/src/components/search/SearchPage.tsx`、`SearchBar.tsx`、`SearchPopover.tsx`），切英文能生效。
  **仍未接线的是那些"还没有键"的文案**：首页两个面板的说明文字、探索轮次的全部文案、
  `formatTime` 的相对时间（刚刚 / N 分钟前 —— 它是纯函数，接线得先把 `t` 传进去）、
  以及错误摘要的安全文案。这些保持硬编码，需要时按批新增键。
  接线原则是**中文界面文案逐字不变**（值本就与组件一致的直接接；只有「前往设置」
  与既有键不同才新增键）。**唯一一处刻意的例外**：搜索框非首页态 placeholder
  从「搜索话题、人物或产品」改用了 locale 里更完整的既有文案
  「搜索一个话题、人物或产品…」—— 与其反过来把翻译改差，不如用这一版。
- 拼错 i18n 键时 i18next **不报错**，而是把键名当文案渲染出去（用户看到 `search.xxx`）。
  `tests/test_webui_ui_contract.py` 的 `test_i18n_keys_used_in_source_exist_in_every_locale`
  专治这个（扫源码里的 `t("ns.key")` 回查 locale）；同文件的
  `test_locales_define_the_same_keys` 保证两种语言的键集合一致。
- 结果卡片的活动指标来自各平台不同字段，缺失时显示为空而不是 0；知乎不返回收藏数、
  B 站投币只在详情里 —— 这些缺口是平台侧的，不做额外请求补齐。
- 并发上限：搜索时每个平台一个 worker 子进程，账号操作与搜索互斥（见
  `docs/features/extension-login.md` 的排他租约）。

- 结果内筛选不再清空勾选（2026-10-21）：`filters` 是每次按键都新建的对象，放进重置依赖会让"先勾选 → 再筛选 → 批量操作"这个顺序直接失效（每敲一个字选择被清空、批量条整块消失）。现在只在换任务 / 换平台 / 外部要求重置时清空；被筛掉但已勾选的项本来就不计入批量计数。
- 错误态轮询退避（2026-10-21）：后端重启或持续 5xx 时按失败次数指数退避（0.8s 起、封顶 15s），不再固定每 0.8 秒硬撞一次。
- **结果视图按"结果集合是否变化"缓存**（2026-11-05）：`interleave_results()` 内含跨平台去重（两两比对 + 纯 Python Levenshtein），条数一多就是 O(n²) 同步 CPU。以前 `response_results()` 在 job 未终态时**每次** GET 都重算，而长轮询会高频调用它 —— 80 条实测单次 ≈130ms，补全阶段 800ms 轮询 150 秒相当于在事件循环里白烧 20 秒。现在 `_ActiveJob._preview_results` 缓存运行期视图，`add_result()` 变化时作废；`update_snippet()` / `update_metrics()` 就地改同一批对象，不需重建。
- **去重本身做了三处剪枝**（2026-11-05，结果不变，随机 300 组用例与旧实现逐一比对一致）：
  1. 归一化标题/摘要**每条只算一次**（原来每两两配对重算，80 条一次去重执行 10 万+ 次 NFKC）；
  2. 长度比预筛 —— Levenshtein 相似度上限是 `min_len/max_len`，够不到阈值就不进动态规划；
  3. 公共前缀+后缀预筛 —— 编辑距离下界 `max_len - (前缀+后缀)`，够不到阈值直接返回；
  4. 摘要完全相同走快速判定（两个平台返回同一段文字是最常见情况）。
  合计：独立标题 80 条 118ms → 17ms，重复标题 66ms → 10ms，长摘要场景 280ms → 15ms。
- **`partial` 也是平台终态**（2026-11-05）：`TERMINAL_PLATFORM_STATUSES` 现在是唯一来源（此前 `set_platform_status` 与 `_compute_overall` 各写一份）。`partial` 表示"拿到部分内容就停了"，算成功的一种，但整轮报 `partial` 而不是 `completed`。之前它合法却不在终态集合里：一旦有 worker 发 `partial`，平台就永远停在 `running`，前端轮询不停、结果永不进缓存。
- **平台"返回了内容但全被判重"不再报成普通 empty**（2026-11-05）：分页参数失效或平台限流后回吐同一批时，`PaginationRun.duplicates > 0` 且 `items_seen > 0`，worker 会带上「平台重复返回相同内容，可能是分页暂时失效」的安全原因。普通 `empty` 会让前端**自动取消该平台勾选**并写进偏好，用户下次再也搜不到它且无从排查。
- **小红书推荐词/热搜词占位项在适配器层就被丢掉**（2026-11-05）：占位项自带 `id`（如 `rec1`），只判 id 存在会把它们当笔记输出成点开即 404 的假卡片，还挤掉真实名额。`media_platform/xhs/core.py` 的搜索路径一直有 `rec_query`/`hot_query` 过滤，但聚合搜索的分页路径（`aggregate_search/pagination.py`）直接调 `adapt()` 绕过了它 —— 现在适配器兜底。
- **单结果平台的 rank 分取中性值**（2026-11-05）：`relativeRankScore` 在「组内只有一个不同取值」时返回 0.5。原实现 `value === 0 ? 0 : 1` 把「平台内 rank=0 的唯一一条」判成最差分，而 rank 是 0 起的 —— 于是「某平台只命中一条」的内容被系统性压到底部（每平台数量设 1、筛选后每平台剩一条都会遇到）。

- **渲染路径不再每帧重算**（2026-11-05，纯性能，行为不变）：
  - `selectSearchPresentation` 包 `useMemo([state])`；单平台重搜的
    `mergeSinglePlatformRetry` 结果按 `job_id + revision + 目标平台 + 条数` 缓存 ——
    内容没变就不重跑跨平台去重（这条以前在渲染期无缓存执行）。
  - `ResultTabs` 的过滤与平台计数合并成一次（原来每按键两遍全量过滤 + 两遍
    `groupZhihuQuestions`）；`matchesFilters` 的 query 归一化提到循环外。
  - `ResultCard` 用 `memo` + 稳定比较器包住；`useLayoutEffect` 依赖从
    `result.metrics`（每帧新对象）换成稳定标量，不再每帧重建 ResizeObserver。
- **顺序冻结覆盖搜索阶段**（2026-11-05）：以前只有补全阶段（`hydrationStatus !==
  "not_started"`）冻结，搜索进行中每来一条新结果就整表重排，用户正要点的卡片会跑掉。
  现在首条到终态之间新结果只追加在末尾；换任务/标签/排序/改筛选才重排。
- **轮询失败不再当终态错误**（2026-11-05）：后端重启/瞬时 5xx 时用次要样式并说明
  "正在自动重试"，按钮改为「立即重试」（重新提交本任务）；只有 `createError` 或
  任务已终态时才显示致命错误与「重试」（后者会清空当前结果）。
